# SemBench / agent_bench harnesses

The numbers are in the main README and in docs/DESIGN.md §9; this file is the operating protocol: where the
queries come from, how to rerun every system, and the notes behind each table. First, the rules for recording
a new run:

0. **Record SemBench one query at a time** (`swan_ecomm.py --serial`, `swan_movie.py --serial`; MMQA's runner is
   serial already). The concurrent default launches every query at once -- up to 14 x 20 in-flight two-image
   requests on ECOMM -- which the provider answers with 429s and connection errors and which also inflates
   every per-query latency with contention. The concurrent mode is for cache replay only.
1. **Never rebuild the engine while a run is in flight** -- each query spawns a fresh CLI, so a
   mid-run rebuild silently mixes two binaries.
2. **Back-to-back recording for any latency claim.** Record the compared systems per query, LOTUS then
   SWAN (and PLOP / BlendSQL where they run), into a fresh store through a second proxy (`CACHE_PROXY_PORT=4011 CACHE_DB=<new file>`,
   alias OFF), then merge with `serve/merge_cache.py` (migrates `recorded_at`, upserts, self-verifies).
   The proxy inserts `ON CONFLICT DO NOTHING`, so the main cache cannot be "repopulated" in place.
3. **Back up the results files first.** Every runner overwrites its `*_results.json` per query.
4. **Check `pmset -g log` for a laptop sleep** across the run; find recordings that overlap it with
   `recorded_at - latency < wake AND recorded_at > sleep` (`recorded_at` is UTC) and rerun that query.
5. **A provider error aborts a LOTUS query outright**; rerun it against the partial store -- completed calls
   replay, only the remainder is fresh.
6. **Always score a run.** A drop in calls can hide broken queries.
7. **agent_bench needs the proxy started with `CACHE_ALIAS_CHAT=1`.** SWAN and PLOP send prompt-identical
   user text under different envelopes; the alias serves SWAN's request from PLOP's recorded sample keyed on
   the user text alone, so both engines consume the same verdict *and* the same recorded latency. Without it
   ~98% of SWAN's agent_bench prompts miss, go to the provider fresh, and the verdicts (and the quality
   score against PLOP's ground truth) drift -- an easy way to burn a dollar and get a wrong table.
   SemBench does not use the alias (its SWAN prompts are stored under their own keys).

## Where the queries come from

| suite | SWAN | LOTUS | ground truth |
|---|---|---|---|
| ECOMM | translated by hand from SemBench's BigQuery + LOTUS dialects with the same prompt text and the same relational pre-filters (`swan_ecomm.py`); q10/q11's single-product filters put the image (and description) BEFORE the instruction, the engine's shared-input-first convention | **SemBench's own LOTUS dialect scripts, vendored unmodified** except q10/q11, whose single-product filter prompts carry the same image-first order as the SWAN copy (`ECOMM/lotus_queries/qN.py`, their `run(data_dir)` is called as-is); Palimpzest attaches the image as a field, so its copy has no order to change | SemBench's `toml/` specs + `ground_truth/`, regenerated by `gen_ground_truth.py` |
| MOVIE | translated from SemBench's LOTUS runner templates verbatim (`swan_movie.py`: sem_filter → `ai_filter`, sem_join → join + `ai_filter`, sem_map → `ai_classify` / `ai_score`) | [**SemBench's official `movie/lotus_runner.py`**](https://github.com/SemBench/SemBench/blob/main/src/scenario/movie/runner/lotus_runner/lotus_runner.py), re-expressed query by query in `lotus_movie.py` with the same templates, `head()` limits and the sem_map scoring variant | `MOVIE/gold/` from SemBench's `queries/gold_sql/` via `gen_ground_truth.py` |
| MMQA | translated from SemBench's BigQuery dialect (`AI.IF` → `ai_filter`, `AI.GENERATE` → `ai_complete`; `swan_mmqa.py`); q6 adds one sentence pinning the answer to the listed destinations, without which the model answers from what it knows about the airline | **written by us** — SemBench MMQA ships no LOTUS runner; `lotus_mmqa.py` mirrors the same table/prompt mapping as the SWAN queries so the comparison is engine-vs-engine (q2a, q2b, q6 and q7 carried their own wording until 2026-11-23) | SemBench's `ground_truth/` |
| agent_bench (PLOP) | translated from PLOP's queries (`AGENTBENCH/plop_queries/`, `translate_to_swan.py`), which ship in the authors' public fork [Morrila](https://github.com/DMoRanSky/Morrila); PLOP runs from that fork (`PLOP_FORK.md`) and its side is the committed `results/plop*`. Q29/Q30 have LIMITs inside CTEs with no ORDER BY, so every system's copy orders them by key | **written by us** (`AGENTBENCH/lotus_queries/QN.py`; PLOP is the compared system here, LOTUS is a third reference) | PLOP's un-rewritten execution of the LIMIT-free queries (`plop_gt_queries/`, `results/plop_gt/`) |

PLOP and BlendSQL: on MOVIE, `MOVIE/plop_queries/qN.sql` and `MOVIE/blendsql_queries/qN.sql` carry the same
prompt text as the SWAN queries in each system's own dialect (PLOP appends its answer-format suffix, BlendSQL
its `LLMMap` frame); on agent_bench, `AGENTBENCH/blendsql_queries/QN.sql` is the mechanical translation of
the SWAN queries (`translate_to_blendsql.py`). Neither supports images, so ECOMM and MMQA are not run for
them. Running the PLOP fork: `PLOP_FORK.md`.

Sema: its repository ships no SemBench queries, so `MOVIE/sema_queries/qN.sql` carry the SWAN queries' prompt
text in its `s'...'` dialect; on agent_bench, `AGENTBENCH/sema_queries/QN.sql` is the mechanical translation of
PLOP's queries (`translate_to_sema.py` documents the mapping). Sema takes no images, so ECOMM and MMQA are not
run for it.

Palimpzest: `MOVIE/palimpzest_queries.py`, `MMQA/palimpzest_queries.py` and `ECOMM/palimpzest_queries/qN.py`
are **SemBench's own Palimpzest programs**, copied from the SemBench repository (MOVIE q1–q10, MMQA all
eleven, ECOMM q1–q13, of which q12 is changed, see ECOMM below; SemBench wrote none for ECOMM q14, so
`ECOMM/palimpzest_queries/q14.py` is **our program**, the same shape as the SWAN and LOTUS copies: white-socks
filter, join on the description, best image per product), run by `palimpzest_<suite>.py` through
`palimpzest_exec.py` in Palimpzest's own interpreter (`setup_palimpzest.sh`) with SemBench's Palimpzest
settings and the Abacus optimizer's pareto plan search (SemBench ran 0.8.2 with it off; we run 1.5.3, the
current release); Palimpzest's sample-based cost estimation runs only with a validator or training set,
which the suites do not supply, so its default cost model decides and no sampling calls are made.
Calls and tokens are the proxy's counter deltas while a query runs (one suite at a time, nothing else on the
proxy); cost is computed from those tokens at list price.

On agent_bench Palimpzest runs `AGENTBENCH/lotus_queries/QN.py` unchanged through `palimpzest_hybrid_exec.py`, which backs the
programs' `sem_filter` / `sem_map` with Palimpzest programs (the prompt's labelled fields become
`depends_on` columns, the rest the instruction), so the LOTUS and Palimpzest rows share one formulation.

So on ECOMM and MOVIE the LOTUS side is SemBench's own code; on MMQA and agent_bench it is our translation, kept prompt-identical to the SWAN side.

SWAN 2.0 (`SWAN2/`): the benchmark at github.com/ZhaoFuheng/SWANBench writes one AISQL query per question that
every system runs; `SWAN2/aisql`, `SWAN2/oracle` and `SWAN2/questions` are a copy of its queries, oracle forms
and question list (`SWAN2/sync.sh` refreshes them from a checkout), kept here so this repository holds every
query behind its tables. The databases, harness, translations and results live in the benchmark.

## What is on disk vs. what you need to fetch

Committed: every query (SWAN, PLOP, PLOP ground-truth, LOTUS), the harnesses, gold/ground truth, the small
suite databases (`ECOMM/ecomm.db`, `MOVIE/movie.db`, `MMQA/mmqa.db`), the agent_bench datasets
(`AGENTBENCH/dataset/`, TPC-H sf0.005 parquet + book_review/yelp/googlelocal/stockindex), the per-run
summaries (`*_results.json`, comparison `.md`) and the result rows of the cited runs
(`AGENTBENCH/results/{plop,plop_gt,lotus,blendsql,palimpzest,sema,swan_20261111}`; the large Q19 outputs are gzipped and
the scorer reads `.csv.gz`).

Not committed (images, raw sources, caches):

- `ECOMM/data/sf_500/images/` -- 500 product images. `ecomm_prepare.py` rebuilds `data/sf_500/` from the
  SemBench ECOMM source (Kaggle fashion-product-images); the parquet tables + `image_files.txt` are committed,
  only the image files are missing, so text-only queries (q1, q3, q5, q7) run as-is.
- `MMQA/files/mmqa/source_data/` and the image files under `files/mmqa/data/` -- from the SemBench MMQA
  release; the sf_200 CSVs that `setup.sql` reads are committed.
- `serve/.llm_cache.duckdb` -- the recorded LLM answers of every system on every suite (latency + cost replay);
  `serve/fetch_cache.sh` downloads the published copy. Without it every run is fresh against the provider; with
  it, reruns are free and latency-faithful.

Runners default to `../../build/release/duckdb`; set `DUCKDB_BIN` to use another build (e.g. reldebug).

Runners: `MOVIE/swan_movie.py --serial`, `ECOMM/swan_ecomm.py --serial`, `MMQA/swan_mmqa.py`;
`*/lotus_*.py`; `AGENTBENCH/swan_agentbench.py` + `eval_agentbench.py` (deterministic GT). Each takes
query ids as arguments.

LOTUS's runners (`lotus_movie.py`, `lotus_ecomm.py`, `lotus_mmqa.py`, `AGENTBENCH/lotus_agentbench.py`) replay their
recordings only under the versions that made them, lotus-ai 1.2.4 with litellm 1.92.0: a newer litellm renders the
request body differently, so the same prompts miss the cache and run fresh. `setup_lotus.sh` builds that environment
in `aisql-bench/.venv-lotus` (from `requirements-lotus.txt`); run the LOTUS runners with its interpreter.

## Reproducing the README tables

**Python environment.** The serving stack and the harnesses are Python; `.python-version` pins **3.12** (any
≥ 3.11 works). With [uv](https://docs.astral.sh/uv/) the pin is honoured automatically and the interpreter is
downloaded if missing:

```sh
uv venv                                      # creates .venv on Python 3.12 (git-ignored)
                                             # without uv: python3.12 -m venv .venv
source .venv/bin/activate
uv pip install -r requirements.txt           # litellm, duckdb, pandas
uv pip install -r requirements-embed-st.txt  # embedding server (MiniLM for text + CLIP for images)
aisql-bench/setup_lotus.sh                   # only to run the LOTUS baselines: their own environment, aisql-bench/.venv-lotus
```

(`pip install -r ...` works the same without uv.) Activate the environment in every shell that runs
`serve/start_stack.sh` or a harness — they use whatever `python3` / `litellm` is on PATH. Keys go in `.env`
(`docs/GUIDE.md`); without a key the cache replays every recorded run. Start the stack with
`serve/start_stack.sh` (litellm :4000, cache proxy :4001, embedding server :4002); it reuses a service it finds
running, so stop the proxy (`pkill -f ai_cache_server.py`) before starting it in another mode. To replay without
the recorded latency, start it with `CACHE_SIMULATE_LATENCY=0 serve/start_stack.sh`: latency then measures only
the local machine. The tables are defined at the recorded pace; without it call counts move by about 1%, a few
requests can miss the store, and PLOP and BlendSQL (one connection per request) can run out of local ports on
macOS. Every call goes through the proxy, so a run that matches the
recorded prompts replays answers, latency and cost for free; a first run with a different model or prompt pays
the provider.

**SemBench MOVIE** (10 queries over 2,000 Rotten Tomatoes reviews; data, queries, gold answers and every
system's recorded results are in the repo). SWAN (about 25 minutes replayed; $2.25 recorded):

```sh
cd aisql-bench/MOVIE
python3 swan_movie.py --serial              # all 10 queries, one at a time
python3 swan_movie.py --serial q1 q7        # a subset
```

Each query prints latency, LLM calls (`fresh` = not served from the cache), tokens, cost and its quality
metric; the last line is the suite's macro quality. Everything is written to `swan_movie_results.json`
(`SWAN_TAG=_x` suffixes the file names so an experiment never overwrites the baseline). The runner finds
`../../build/reldebug/duckdb` on its own; set `DUCKDB_BIN` for another build.

LOTUS (the official SemBench LOTUS queries, same model, same proxy; about 3 hours replayed because the proxy
replays LOTUS's recorded latency too; $14.45 recorded; needs `../setup_lotus.sh` once; writes
`lotus_movie_results.json`):

```sh
../.venv-lotus/bin/python lotus_movie.py         # all 10 queries
../.venv-lotus/bin/python lotus_movie.py q1 q7   # a subset
```

PLOP and BlendSQL on the same ten queries (`plop_queries/`, `blendsql_queries/`), scored the same way; neither
supports images, so ECOMM and MMQA are not run for them:

```sh
python3 plop_movie.py                       # PLOP_BIN = the Morrila fork's shell, default ../../../Morrila/build/release/duckdb (PLOP_FORK.md)
<python with blendsql> blendsql_movie.py    # e.g. ../../../SWAN_bench/.venv/bin/python
```

Sema on the same ten queries (`sema_queries/`; about 55 minutes replayed; $4.46 recorded):

```sh
../setup_sema.sh                            # once: clones and builds the fork next to this repository (../Sema)
python3 sema_movie.py                       # SEMA_BIN = its shell, if it is somewhere else
```

Palimpzest (PyPI `palimpzest` 1.5.3, MIT DSG's semantic-operator system) on SemBench's own Palimpzest programs
(`palimpzest_queries.py`, copied from the SemBench repository; all ten MOVIE queries), under SemBench's
Palimpzest settings (MaxQuality, parallel execution, 20 workers) with its Abacus optimizer's pareto plan search,
which SemBench had off; Palimpzest's sample-based cost estimation runs only with a validator or training set,
which the suites do not supply, so the default cost model decides. Its calls and tokens are the proxy's counter
deltas while a query runs, so run it with nothing else using the proxy; cost is computed from those tokens at
list price. It runs in its own Python environment:

```sh
../setup_palimpzest.sh                      # once: aisql-bench/.venv-palimpzest with palimpzest 1.5.3 (or set PALIMPZEST_PYTHON)
python3 palimpzest_movie.py                 # ten queries; ../ECOMM/palimpzest_ecomm.py (all 14) and ../MMQA/palimpzest_mmqa.py (all eleven) likewise
```

Compare (per query and in total; works on the committed results before you run anything):

```sh
cd ..                                       # aisql-bench/
python3 compare.py MOVIE
```

It prints one row per query with each recorded system's quality (SemBench's own metric per query: F1,
count/ratio accuracy, Spearman for the ranking queries), calls, latency and cost, and a macro row that is the
README's MOVIE table (for BlendSQL, PLOP and Palimpzest the README's quality is the mean over replays; see the
protocol notes).

**ECOMM and MMQA** (the image suites: ECOMM sf500, 14 queries over fashion product listings with photos; MMQA
sf200, 11 queries over tables that mix text and images; quality = macro F1 / count accuracy / ARI) run the same
way (`ECOMM/swan_ecomm.py --serial`, `MMQA/swan_mmqa.py`, `compare.py ECOMM`), but most of their queries need
the image assets, which are not in git (see above). PLOP and BlendSQL do not support images, so these suites
compare SWAN with LOTUS on the full suite and with Palimpzest on SemBench's programs for it: Palimpzest runs
SemBench's own programs for ECOMM q1–q13 and our program for q14 (SemBench wrote none; it mirrors the SWAN and
LOTUS copies) and all of MMQA; its cost is computed from its tokens and its latency is the execution time it
reports, without its interpreter's start-up. One SemBench program is changed: ECOMM q12 asked one generated
text field for the whole JSON, which Palimpzest returned empty or as a parsed object for every product (0.0
whatever the answers); ours generates the brand and the category in the same call and assembles the JSON from
them and the product id, as the SWAN query does.

**Hybrid bench (agent_bench Q1–Q30).** The 30 hybrid queries (relational plans with semantic operators over
DataAgentBench and TPC-H data) are the benchmark introduced by the PLOP paper; the queries and data ship in the
authors' public fork, [Morrila](https://github.com/DMoRanSky/Morrila), and PLOP runs from it (`PLOP_FORK.md`:
clone, patch, build). Every system's queries and results are committed under `AGENTBENCH/`. To rerun and compare:

```sh
pkill -f ai_cache_server.py                    # start_stack.sh reuses a running proxy: stop it to change its mode
CACHE_ALIAS_CHAT=1 serve/start_stack.sh        # shared-verdict mode: SWAN's bare prompts key on the text PLOP sent, so
                                               # SWAN replays PLOP's recorded verdicts (rule 7 above)
cd aisql-bench/AGENTBENCH
python3 swan_agentbench.py                     # SWAN Q1..Q30 (~12 min; a first run pays $0.30 to the provider)
python3 swan_agentbench.py Q16 Q17             # a subset
../.venv-lotus/bin/python lotus_agentbench.py  # LOTUS Q1..Q30 (our translations, lotus_queries/; ~30 min replayed, $3 recorded)
<python with blendsql> blendsql_agentbench.py  # BlendSQL Q1..Q30 (translate_to_blendsql.py; ~35 min, $3)
python3 palimpzest_agentbench.py               # Palimpzest Q1..Q30 (the LOTUS programs, operators served by Palimpzest; ../setup_palimpzest.sh first)
python3 sema_agentbench.py                     # Sema Q1..Q30 (translate_to_sema.py; ../setup_sema.sh first; ~3.6 h replayed, $20 recorded)
python3 eval_agentbench.py swan lotus plop blendsql palimpzest sema   # quality of each vs the LIMIT-free ground truth
SWAN_TAG=swan python3 report_three_way.py      # per-query table of every system -> results/agentbench_comparison_three_way.md
                                               # (the committed table is SWAN_TAG=swan_20261111, the run behind the README row)
```

The SWAN translations are `swan_queries/Q*.sql` (`translate_to_swan.py` documents the mapping). Runs are tagged
(`SWAN_TAG=my_run` → `results/my_run/` + `results/my_run_agentbench_results.json`) and scored by tag:
`python3 eval_agentbench.py my_run plop`. The runner sends `ai_filter`'s prompt bare, so the proxy's alias serves
PLOP's recorded verdict to SWAN; without it a run samples the model anew (rule 7).

**SWAN 2.0.** [SWAN 2.0](https://github.com/ZhaoFuheng/SWANBench) is a 120-question benchmark over four BIRD
databases: one AISQL query per question, which every system runs as written, so each system's planner decides
the LLM calls. Its `scripts/run_swan_aisql.sh` clones and builds this repository, starts the serving stack and
runs all 120 questions; the per-question answers, scores and seconds are under `results/gpt-5.6-luna/` in that
repository. The 120 queries are also kept here under `SWAN2/`.

## Protocol notes behind the README tables

- **Every table.** A row is one full pass of one system over the suite on one machine (a MacBook Air M5,
  November 2026), replayed: the cache proxy answers each request from `serve/.llm_cache.duckdb` after its
  recorded response time and has no provider behind it (`CACHE_UPSTREAM=http://127.0.0.1:9`), so a prompt that
  was never recorded fails instead of being asked. Quality, calls and cost come from the store alone; latency
  is the recorded response times plus the system's own work on that machine.
- **LOTUS** runs with its own response cache on, emptied before each query (`LOTUS_CACHE=0` turns it off); it
  served no request on any of the five benchmarks.
- **Palimpzest** runs with three pins that keep its prompts identical from run to run, so they match the
  recordings: `PYTHONHASHSEED=0` (its system prompt lists an operator's input types in set order), its
  sequential executor for MMQA q5 (one call over sixteen rows, which must arrive in table order) and a
  tie-break by image id in ECOMM q14 (our program). The runners set all three.
- **Sema** runs the authors' fork at commit a86cb62 with its default settings, where a lone semantic filter or
  map asks one row per request. `sema_fork.patch` makes it build on macOS and holds it to the 20 requests in
  flight every system gets.
- **SWAN-AISQL (Jev)** is `run_sembench_typesafe.sh`: `SET ai_typesafe='filter,classify'` (MOVIE:
  `'filter,classify,score'`) with model `jev-latest`; image-bearing prompts, `ai_complete` and `ai_agg` stay on
  `gpt-5.6-luna`. Its recorded TypeSafe answers replay from the store like any other call. Per query:
  `typesafe_comparison_20261120.md`.
- **MOVIE.** Quality = the suite's macro F1 / count accuracy / Spearman. Palimpzest runs SemBench's own
  Palimpzest programs under its Abacus optimizer; its latency is the execution time it reports per query,
  without the start-up of its own interpreter. Four queries (q1, q2, q5, q6) end in a LIMIT with no ORDER BY.
  BlendSQL, PLOP and Palimpzest return the first rows whose answers arrive, so their score on those queries
  changes from one replay to the next; the table gives their quality as the mean of eleven replays
  (`python3 MOVIE/limit_draws.py` prints it with the range; `run N` records more). The other systems return
  the same rows every time.
- **Hybrid bench.** Quality = row-multiset F1 against the LIMIT-free ground truth, i.e. the public Morrila
  fork's un-rewritten execution (`AGENTBENCH/results/plop_gt`, `plop_gt_queries/`). SWAN and PLOP consume
  the same prompt template, and every system's prompts are answered from one recorded cache, so a verdict
  never differs between two executions of the same prompt; that is why PLOP-DP scores 1.000 here where the
  PLOP paper reports 0.848 against the same reference (there the optimized and unoptimized plans sampled
  gpt-5-mini separately, and the gap is the model's run-to-run variance, not the rewrite). LOTUS's,
  BlendSQL's, Palimpzest's and Sema's verdicts are independent samples, so where an answer hinges on
  a few judgments any disagreement scores 0. A LIMIT with no ORDER BY below a semantic function decides which rows
  the function is asked about, so that input depended on the engine and the machine; every system's copy
  orders those LIMITs by key (Q15-Q19, Q25, Q27-Q30), the only edit to the queries. The list and the rule are in
  [PLOP_FORK.md](PLOP_FORK.md). BlendSQL runs our mechanical translation of the SWAN queries
  (`AGENTBENCH/translate_to_blendsql.py`). Palimpzest runs the LOTUS programs unchanged with their semantic operators served by Palimpzest
  (`palimpzest_hybrid_exec.py`), its Abacus optimizer choosing each operator's plan.
- **SWAN 2.0.** Quality = relative error / F1, as in SemBench; the databases are scaled to ~10k rows with
  duplicate entities. The benchmark itself lives in [SWANBench](https://github.com/ZhaoFuheng/SWANBench).
